# Счётчик: поведенческий счёт полученного

Инспекторы фазы запроса судят о **намерении**: что клиент прислал. Счётчик
судит о **результате**: что клиент унёс. Скрейпер, перебирающий каталог по
одному честному запросу, для сигнатур неотличим от покупателя — отличает их
только сумма: тысяча объектов на адрес за минуту. Эту сумму никто в контуре не
держал; счётчик — её держатель.

Один инспектор на двух фазах одного subject. Фаза ответа **меряет**: правила
`measure` профиля превращают ответ в заряды именованных корзин. Фаза запроса
**судит**: правила `judge` сравнивают уровни корзин с порогами и отвечают
`score`/`deny` либо действиями соседям. Реакция приходит на *следующем*
запросе субъекта, и это осознанная граница: ответ, переливший корзину, уже
сгенерирован, а предыдущие уже ушли — блокировать его значило бы удвоить
модель ради последнего килобайта.

Реализация — inspectors/counter (`inspectors/counter`), скелет json,
корзины капчи.

## Счётчики: объявляются на инспектор, не на профиль

Счётчик — семейство корзин, по одной на пару (ось, субъект). Объявление —
имя, оси, ёмкость и потери каждой оси — живёт в общей секции
`profiles/_shared/counters.yaml`, одной на инспектор:

```yaml
counters:
  api_objects:
    unit: obj
    axes:
      ip:      { max: 1000, loss: 2 }   # ёмкость в натуральных единицах,
      asn_net: { max: 5000, loss: 2 }   # потери -- % ёмкости в секунду
      sess:    { max: 800,  loss: 2 }
  abuse:
    fill: note                          # наполняют соседи, не measure
    axes:
      ip:      { max: 100, loss: 0.5 }
  sessions:
    axes:
      sess:    { max: 300, loss: 1 }
    subjects:                           # свои источники ключей: «на эту куку
      sess: { cookie: waf_sid_default } # заведён счётчик» видно в объявлении

subjects:
  sess: { cookie: waf_cid }             # умолчание -- кука клиренса капчи
  user: { from: "header:x-api-key" }    # cookie:<имя> | header:<имя>
                                        # | session:user | session:sid
```

`fill` объявляет владельца шкалы: `measure` (умолчание) — корзину наполняют
собственные правила фазы ответа, `note` — просьбы соседей по каналу действий.
Ровно один вход на корзину: мерная не принимает `note`, сигнальную нельзя
мерить — уровень обязан объясняться одним владельцем. Судят правила `judge`
оба вида одинаково.

Из «общие на инспектор» следует и всё остальное. Ключи Redis — без профиля:
`cnt:bkt:<счётчик>:<ось>:<субъект>`, поэтому маршруты с разными профилями
намеренно греют один счёт — «получил много объектов» это факт про субъекта, а
не про маршрут. Это сознательное отличие от корзин капчи, где профиль в ключе
разводит ёмкости разных маршрутов: здесь ёмкость — свойство объявления, и оно
одно. Профили ссылаются на счётчики по имени; ссылка на необъявленный счётчик
или ось **отвергает поколение целиком**, как любая опечатка профиля.

Хранение — арифметика корзин капчи без изменений
(`docs/inspectors/captcha/buckets.md`): GCRA в сдвинутых координатах во
внутреннем Redis контура, заряд — атомарный `INCRBYFLOAT`, потери считаются из ответа,
пол и потолок держит срок ключа. Redis недоступен — экземпляр считает в своей
памяти той же арифметикой и возвращается на общий счёт, когда Redis отвечает.
Пакет скопирован (`internal/buckets`), как protocol и queue.

Смена `max`/`loss` живого счётчика — транзиент: сдвинутые координаты считаются
от rate, старые ключи после смены дают мусор, но клампы `[0, max]` и коррекции
границ выправляют его за время жизни ключа. У капчи при правке профиля — то же
самое; ничего не делается намеренно.

### Оси

| Ось | Ключ | Откуда |
| --- | --- | --- |
| `ip` | адрес `/32` (`/128`) | из сообщения |
| `asn_net` | эффективный анонс, в который попал адрес | кодер гео по gRPC, синхронно и в бюджете сообщения; кэш кусками, не анонсами |
| `asn_router` | номер автономной системы этого анонса | там же |
| `sess` | хеш куки | имя куки — `subjects.sess.cookie`, умолчание `waf_cid` |
| `user` | хеш настраиваемого значения | `subjects.user.from`; пусто — ось выключена |

Источники `sess`/`user` — общие на инспектор, но объявление счётчика может
назвать свои той же секцией `subjects:` внутри себя: так один счётчик заведён
на куку клиренса капчи, соседний — на куку сессии калитки (`waf_sid_<профиль>`,
имена живут в профилях этих инспекторов), и живут они независимо. Два счётчика
на одной куке делят одно чтение значения. Свои источники печатаются в
`counters.yaml` только когда объявлены — старый инспектор с `KnownFields`
такое поколение отвергнет, поэтому имя куки в объявлении требует
пересобранного образа.

### Ось `user`: ключ клиента или личность

У `subjects.user.from` четыре формы, и они делятся надвое:

| Форма | Ключ | Что это |
| --- | --- | --- |
| `cookie:<имя>` | хеш значения куки | то, что прислал клиент |
| `header:<имя>` | хеш значения заголовка | то же |
| `session:user` | хеш логина | личность от калитки: корзина на человека |
| `session:sid` | хеш `sid` сессии | личность от калитки: корзина на вход |

`cookie`/`header` — стабильные ключи, а не проверенные личности: подпись
клиренса проверяет капча, чужие токены сюда тащить не надо. Вращающий куку бот
уходит от `sess`, но не от `ip` и `asn` — оси для того и несколько. Значения
уезжают в ключ хешем: класть токены клиентов в ключи Redis незачем.

`session:*` берёт то, что о клиенте сказала калитка, — секцию `sessions`
сообщения модуля
(модуль → инспектор (`docs/messages/module-inspectors.md`)).
Подделать такой ключ клиент не может, перевыпуск куки (`/renew`) его не меняет,
а `session:user` сводит все устройства и все сессии человека в одну корзину —
именно то, чего кукой добиться нельзя. Условия у него три:

- **калитка обязана стоять на этом маршруте** и в своей фазе — раньше
  счётчика, меньшим номером волны: волна, которая уже высказалась, ничего
  дослать не может. На фазе ответа и на кадрах секция приезжает сама — она
  сквозная;
- **берутся только записи с `verified: true`**: непроверенная — это то, что
  прислал клиент, и ключом счёта она не становится;
- записей бывает несколько (две калитки, своя сессия и сессия приложения) —
  побеждает наименьшая пара (отправитель, источник), чтобы ключ субъекта не
  прыгал от запроса к запросу. Пассивная калитка не называет никого.

Личности не нужен снимок заголовков: `waf_capture request headers` ось
`session:*` не требует, в отличие от `cookie`/`header`.

Все три условия проверены сквозняком с живой калиткой — логические кейсы
`counter-user` и `counter-user-silent` (`tests/logic/README.md`): в первом
корзина ключуется логином и отказ приходит человеку с другого адреса, во
втором четыре способа остаться без субъекта (калитки нет, калитка пассивна,
калитка позже счётчика, подпись не проверялась) дают одно и то же — правило
молчит. Кадры — `counter-user-frames`, цена пути под нагрузкой —
`tests/load/cases.mjs`.

Заголовок `X-WAF-User` источником быть не может, и это не недосмотр: правки
заголовков ложатся в запрос на `apply`, то есть после всех волн фазы, а снимок
для обменника снят раньше. В нём лежит то, что прислал клиент, — ключ, которым
управлял бы он сам.

## Фаза ответа: учёт

```yaml
response:
  enabled: true
  measure:
    - if:
        status: [200]
        content_type: ["application/json", "+json"]
        methods: [GET]
      source: regex_count
      regex: '"object_id"\s*:'
      counter: api_objects
    - if: { content_type: ["application/json", "+json"] }
      source: size_kb
      counter: json_kb
      axes: [ip]
```

Правило — предикат, источник, счётчик. Предикаты (`status`, `content_type`,
`methods`) — пустое поле означает «любой». Пути в предикате сознательно нет:
разное поведение на разных путях — это разные профили на разных маршрутах, а
не селектор внутри правила. Источники три:
`const` — единица на ответ, `regex_count` — вхождения выражения в теле,
`size_kb` — размер тела. `per` — множитель, минус снимает («хороший ответ
возвращает кредит»). `axes` сужает заряд; пусто — все объявленные оси
счётчика. Правила накопительные: заряжают все совпавшие, одним `Apply` одним
pipeline.

Вердикт фазы — **всегда `allow`**: измеритель не должен стоить маршруту ни
одного запроса, как инспектор действий.

Что здесь решено сознательно:

- **`size_kb` берётся из локатора, не из тела.** Размер там полный, даже когда
  содержимое обрезано превью или снято как `body=meta` — маршруту с одними
  размерными метриками тело можно не возить вовсе.
- **`regex_count` считает по превью, и это осознанный недосчёт.** При
  `complete: false` считается что приехало: недосчёт — fail-soft, на объёме
  утечка всё равно набегает. Флаг усечения уезжает в аудит рядом со значением.
- **Отказанные запросы корзин не греют** — фаза ответа до них не доезжает.
  Правильная семантика: считается то, что субъект реально *получил*.
- **`waf_response_bypass` (sse, upgrade, oversize) — слепое пятно**: фаза не
  бежит, метрик нет. На стриминговых маршрутах счётчик ответов не работает.
- **Ключи субъектов — из контекста запроса** (`request_store.headers`): куки
  живут в запросе, к какой бы фазе ни относилось сообщение. Осям `sess`/`user`
  нужен `waf_capture request headers` на маршруте — кроме `user` с источником
  `session:*`: личность приезжает секцией `sessions` самого сообщения, и
  снимок ей не нужен.

## Фаза запроса: суд

```yaml
request:
  enabled: true
  judge:
    - { counter: api_objects, axis: ip,   at: 60, action: score, score: 40,
        code: CNT_SCRAPER }
    - { counter: api_objects, axis: sess, at: 90, action: deny,
        code: CNT_EXFIL }
  deny_response: counter_limit
  outcomes:
    - { on: score, at: 40, to: captcha, do: challenge, code: CNT_SCRAPER }
    - { on: deny, list: blacklist, write: addr, ttl: 1h }
```

Пороги — проценты заполнения, как `captcha_at` у капчи: натуральные единицы у
каждого счётчика свои, а процент читается одинаково. Уровни всех упомянутых
корзин читаются одним `Apply`; побеждает самое строгое из совпавших правил —
`deny` поверх любого `score`, больший `score` поверх меньшего. Субъекта нет
(куки нет, гео промахнулся) — правило молчит, и это видно в аудите пометкой.

`deny` здесь легитимен ровно потому, что порог написан оператором явно, как
адрес в списке: «решение принято заранее». Но путь внедрения тот же, что у
любого поведенческого инспектора: `mode=passive` на маршруте → `score` → `deny`, когда
распределение уровней на живом трафике посмотрено
(`docs/operations.md`).

У инициатора два вида условия. Первое — **решённый вердикт фазы** (`on: allow
| deny | score`), форма json один в один. Второе — **уровень названной
корзины**:

```yaml
  outcomes:
    - { on: level, if: { counter: abuse, axis: ip }, at: 40,
        list: blacklist, write: addr, ttl: 1h }
```

Оно заведено потому, что вердикт у фазы один, а корзин у счётчика много: по
`on: deny` не отличить, какая из них перелилась. И запись в набор перестаёт
требовать отказа — «уровень дошёл до 40%» законный повод занести субъекта,
ничего не решая про этот запрос. Порог и направление — те же `at`/`below`, что
у счёта; `eq` здесь запрещён: уровень непрерывен, и «ровно 40%» не случается.
Ссылка на необъявленную корзину или ось отвергает поколение, как в `judge`.
Уровни читаются тем же одним `Apply`, что и суд, а каждое сравнение — включая
несработавшее — уезжает в аудит (`outcome_levels`): «почему инициатор
промолчал» разбирают ровно по ним.

Инициаторы -- по решению фазы: просьба соседу либо запись субъекта в живой
набор. Через них счётчик
становится обычным отправителем канала действий: у получателей должны быть
правила `from: "counter"`, капча уже слушает `challenge` и `note` — стыкуется
без единой правки с её стороны. Запись в набор замыкает вторую ступень
лестницы капчи: переливший субъект режется модулем на краю, до шины.

`write` у записи — те же четыре вида, что у всех отправителей
(modsec (`docs/inspectors/modsec/README.md`)):
`addr` — адрес клиента, `net` — эффективный анонс, `net_all` — все анонсы над
адресом, включая чужие широкие, `asn` — состав системы целиком. Анонсы и
состав счётчик спрашивает у того же кодера гео, что и ключи оси `asn_net`
(`WAF_COUNTER_GEO_ADDR`), в момент записи и в бюджете сообщения; пачка уходит
одним кадром keeper, вся или никак. Кодер нужен записи и молчит — ответ
`error` с `COUNTER_GEO_UNAVAILABLE`, исход выбирает `waf_exception` маршрута.

Глаголы отправителя: `challenge`, `threshold`, `skip`, `note`, `reauth` и
`mutate` — последний включает или гасит группы модификаторов у rewrite
(`to: <декларация rewrite>`, повод — `code:`). Плюс четыре управляющих, которые
исполняет сам модуль, а не сосед: `active`, `passive`, `vote`, `off` ставят режим
вызова соседа — те же слова, что у `waf_inspect … mode=`
(`docs/inspector-actions.md`).
У них `to` обязателен, а ось — срок: `request` (до конца транзакции; на
кадре — этот кадр) либо, только в секции `frame`, `conn` — до конца
соединения. Разрешения адресат не спрашивает: просить вправе любой
инспектор на маршруте. На кадрах это лестница квоты: полная корзина
соединения включает rewrite (`active`) и просит его отвечать ошибкой вместо
сообщения (`mutate`) — до просьбы второй волны нет вовсе; полная корзина
адреса пишет адрес в набор — профиль `ws_quota` и прогон `nginx/tests/ws`.

Место на волне — **раньше получателей** своих действий: действия соседям по
своей волне не видны. Судить counter может и первой волной; слать капче —
только стоя до неё.

### Просьбы соседей

Из словаря счётчик принимает `skip`, `threshold` и `note` — та же секция
`trigger.prior`, что у json, с тем же ограничением (послабление требует
имени; потолков в правиле нет, величину просьбы держит отправитель).
`threshold` масштабирует отдаваемый счёт, пороги правил не двигаются. `skip` снимает суд, но **не
учёт**: просьба «не проверяй» не означает «не запоминай», а учёт и так живёт
на другой фазе.

`note` — изменение корзины: `value` — проценты её ёмкости, плюс доливает,
минус снимает, `−100` гарантированно обнуляет (клампы `[0, max]` корзины).
Правило дополнительно называет корзину — только `fill: note` деклараций:

```yaml
trigger:
  prior:
    - { from: modsec, accept: [note], apply: [ip, asn],
        codes: [MODSEC_SQLI], counter: abuse }
```

Что здесь решено сознательно:

- **Грант живёт в правиле, провод только выбирает.** Просьба может назвать
  корзину сама (`counter` на проводе), но это селектор поверх правил приёма:
  названная корзина проходит только через правило, которое её этому
  отправителю и выдало, чужое имя остаётся `no_rule`. Пустой селектор —
  корзину называет правило (`counter:` в строке). Ось провода разворачивают
  декларации: `ip` → `ip`, `asn` → обе ASN-оси (сигнал один, шкалы две),
  `session` → `sess`. Ось `user` с провода недостижима — канал такой оси
  не знает.
- **Потолка у `note` нет** — как у корзин капчи: границы держат загрузчик
  отправителя (`value` не шире ±100) и ёмкость корзины.
- **Заряды ложатся на фазе ответа** — там, где все волны фазы запроса уже
  высказались (`prior` сквозная) и где живёт весь учёт, тем же `Apply`. Суд
  остаётся ранним и читает уровень со следующего запроса субъекта — обычная
  граница счётчика. Отсюда же: профиль с правилом `note` и выключенной фазой
  ответа не грузится — правило было бы мёртвым.
- **Отказ самого отправителя заряд не довозит.** `deny` обрывает фазу, и
  действия отказавшего никуда не доезжают: поздних волн нет, доставлять некому.
  А вот отказ **модуля** по сумме счёта заряду не мешает: сосед высказался на
  своей волне, счётчик снял просьбу на своей, и оба отработали до того, как
  модуль сложил счёт и закрыл запрос. Именно так и копятся заблокированные
  запросы -- ради них ранний заряд и сделан.

Прежняя граница «`note` счётчик не принимает: держатель чужих процентов уже
есть — капча» пересмотрена, и разница с капчей проведена по исходу, а не по
глаголу: у капчи перелив кончается проверкой человека, у счётчика — судом с
`deny` и записью в набор. На машинных маршрутах (API-ключи, интеграции),
где проверять некого, работает только второе. Возражение о двух владельцах
одной шкалы сняло `fill`: входов у корзины по-прежнему один.

## Режимы и незнание

Режима у профиля в панели нет: включён ли счётчик и гейтит ли его суд, решает
вызов на маршруте — `waf_inspect … mode=active|passive|vote|off`; контроллер
печатает в YAML `mode: enforce`. Файловый профиль с `mode: observe` загрузчик
ещё понимает: суд считается и пишется (`engine.passive: true`,
`would_verdict`, `would_code`, `would_score`), модулю `allow` с кодом
`COUNTER_OBSERVE`, инициаторы стреляют по решению `enforce`, учёт продолжается
(общий контракт (`docs/inspectors.md`)); файловый `mode:
off` — ни суда, ни учёта, с кодом в аудите.

Незнание — `verdict: error` с кодом `COUNTER_*`: битое сообщение, чужая версия,
неизвестный профиль, чужая фаза, переполнение очереди, истёкший бюджет,
недоступный обменник корзин. Измерения не было, и выбирать за маршрут между
пропуском и отказом счётчик не вправе — исход называет
`waf_exception <фаза> inspector pass|deny`. Прежний `allow` держался на доводе
«счётчик — эвристика, его поломка не должна стоить запроса»: довод верный, но
это решение маршрута, а не инспектора, и на маршруте оно теперь и записано.

`allow` остаётся там, где счётчику нечего делать: профиль выключен, фаза
выключена, просьба соседа сняла проверку.

## Наблюдаемость

Событие `kind=inspector` в `audit_subject`, склейка по `ray`:

- фаза ответа: сработавшие правила measure (счётчик, источник, значение, оси,
  флаг усечения), принятые note (`noted`: корзина, ось, ключ, проценты,
  единицы, повод, отправитель) и уровни корзин после зарядов — по ним видно,
  как близко субъект к порогам, без второго похода в Redis;
- фаза запроса: каждое сравнение judge (корзина, уровень, порог, сработало ли,
  был ли субъект), тройка масштабирования при `threshold`, исходы просьб,
  имена сработавших инициаторов, `would_*` в наблюдении.

**Находка на каждое сработавшее правило суда** (обе фазы и кадры): повод
правила (`code`), корзина с осью (`rule: <счётчик>:<ось>`), место `conn` —
субъект счёта это свойство клиента, а не кусок запроса, — и уровень с порогом
в `evidence`. Строгость по действию: `deny` — `high`, `score` — `medium`;
наблюдение находку не глушит, иначе пороги не по чему калибровать.

Без неё запись события говорила только «отказал счётчик»: повод в записи
модуля не живёт (там класс решения — `inspector`), уровень корзины задним
числом не восстановить (он утёк), а карточка события показывает `engine`
только рядом с находкой. Разбор отказа упирался в «непонятно, что произошло».

Пульс — стандартный кадр присутствия с `config_hash`/`rev`/`apply` поколения.

## Раскатка

Стандартный контур `docs/inspector-config-distribution.md`:
ключ KV `policy/counter`, три слоя, канон хеша без изменений. Общая секция
едет тем же манифестом **псевдопрофилем `_shared`** с единственным файлом
`counters.yaml`: формат манифеста и Parse не меняются вовсе, а загрузчик
каталога читает `_shared/` сам и профилем его не считает. Bootstrap-каталог в
образе устроен так же.

## Границы

| Что | Как |
| --- | --- |
| Где живёт счёт | внутренний Redis контура, точечные ключи; реплики равноправны |
| Реакция | на следующем запросе субъекта; сам перелившийся ответ не блокируется |
| Наполнение | один вход на корзину: `fill: measure` — свои правила, `fill: note` — просьбы соседей |
| Отказанные модулем | до фазы ответа не доезжают и корзин не греют; `deny` соседа не довозит и его `note` |
| Стриминг и bypass | фаза ответа не бежит — метрик нет |
| Кадры (`phase: frame`) | секция `frame` профиля: учёт и суд на одном кадре, см. [Кадры WebSocket](#кадры-websocket) |
| Липкость | не нужна: фазы связывает Redis, а не транзакция |
| Личности | сам не проверяет: `sess` и `user` с кукой/заголовком — стабильные ключи, не identity. Личность берётся готовой у калитки — `session:user` / `session:sid` |

## Кадры WebSocket

После апгрейда модуль спрашивает счётчик на каждом кадре обеих сторон
(`waf_inspect frame counter`, `docs/streaming.md`),
и на кадре счётчик делает обе свои работы разом: правила `measure` секции
`frame` превращают кадр в заряды, правила `judge` той же секции судят уровни
— тем же походом в Redis, поэтому кадр, доливший корзину до порога, получает
отказ сам, а не следующий. Отказ — закрытие соединения кадром Close из
записи `deny_response` секции (`ws_policy` по умолчанию, `type=websocket`).

Секции — форма файла, не панели: в панели правила всех фаз лежат одной
таблицей на каждый вид (учёт, суд, инициаторы) со столбцом «Где» (ответ /
кадры, запрос / кадры), а раскладку по секциям `request` / `response` /
`frame` делает форма при сохранении. Перенос строки между фазами снимает
чужие селекторы и ось `conn` вне кадров.

```yaml
frame:
  enabled: true
  measure:
    - if: { direction: [c2s] }          # кадры клиента штуками
      source: const
      counter: ws_frames
      axes: [conn]
    - if: { direction: [s2c] }          # байты приложения
      source: bytes
      counter: ws_bytes
      axes: [ip]
    - if: { opcode: [text] }            # вхождения в полезной нагрузке
      source: regex_count
      regex: '"id"'
      counter: api_objects
  judge:
    - { counter: ws_frames, axis: conn, at: 90, action: deny, code: WS_FLOOD }
  deny_response: ws_policy
  outcomes: []                          # те же инициаторы, что у суда запроса
```

Селекторы правил на кадрах — `if.direction` (`c2s`, `s2c`) и `if.opcode`
(`text`, `binary`, `continuation`); статус, тип и метод у кадра не бывают,
и загрузчик их отвергает. Источник `bytes` — размер полезной нагрузки в
байтах (работает и на ответе: там это размер тела); `regex_count` читает
полезную нагрузку из обменника по локатору сообщения, `size_kb` и `const` —
как на ответе. Ось `conn` — корзина на соединение: ключ — `conn_id`
рукопожатия, и она есть только на кадрах; правило запроса с этой осью не
загружается. Настраиваемые оси (`sess`, `user`) берут ключи из заголовков
рукопожатия (`request_store`), как фаза ответа — из заголовков запроса; ось
`user` с источником `session:*` — из секции `sessions` самого сообщения: она
сквозная и на кадрах приезжает та же, что на рукопожатии.

Просьбы соседей на кадре принимаются теми же правилами приёма; `note`
снимается на фазе `frame`, если запись сделана на ней. Профиль без секции
`frame` на кадрах ничего не считает и не судит (allow с `COUNTER_MEASURED`),
и печатается контроллером как прежде — без ключа `frame`: такой файл читает и
счётчик, собранный до фазы кадров.

## Чего в первой итерации нет

Суда на фазе ответа («заблокировать перелившийся ответ») — выигрыш мал, модель
удваивается. Метрик фазы запроса (считать и отказанные) — считать их может
только модуль, у инспектора этих запросов нет. Обе — осознанные границы, а не
пробелы. Приём `note` — граница, снятая позже деклараций: см.
[просьбы соседей](#просьбы-соседей).
